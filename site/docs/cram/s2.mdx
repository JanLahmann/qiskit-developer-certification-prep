## Visualize quantum circuits

### One drawer, four renderers, and a signature that does not forgive typos

`QuantumCircuit.draw()` and the standalone `circuit_drawer()` in `qiskit.visualization` are the same machinery: the function form only differs by taking the circuit as its first positional argument. Both choose a renderer with `output=`, and the registry holds exactly four names — `text` (the default), `mpl`, `latex`, `latex_source`. Anything else raises `VisualizationError`, and the message helpfully lists the four; `output="matplotlib"` and `output="figure"` are the two spellings questions like to plant.

Return types are examinable per renderer. `text` hands back a `TextDrawing` object — printable, but *not* a `str`, and not `None` (the ASCII art you see in a notebook is its repr). `mpl` returns a `matplotlib.figure.Figure`, the object you style and `savefig`, which is why `mpl` is the answer to every publication-figure question. `latex` returns a PIL `Image` and needs a LaTeX toolchain; `latex_source` returns the raw LaTeX string. The one exception to memorize: hand the mpl renderer your own axes with `draw("mpl", ax=ax)` and it returns `None`, because the caller already owns the figure.

The signature is closed — there is no `**kwargs` catch-all. A near-miss keyword is a hard `TypeError`, never a silently ignored option: `initial_states=` for `initial_state=`, or `format=` for `output=` on the function form. The kwargs worth knowing cold: `idle_wires=False` deletes any qubit or clbit wire carrying no operations (`idle_wires="auto"` keeps them unless the circuit carries a transpiler layout, so it is only equivalent on transpiled circuits); `reverse_bits=True` flips the top-to-bottom wire order so the highest-index qubit is drawn on top; `initial_state=True` prefixes each wire with its starting `|0⟩` label; `plot_barriers=False` hides barriers. `reverse_bits` and `plot_barriers` work in every renderer, while `fold` (wrap width), `scale`, and `style` are renderer-specific — and `style` is *silently ignored* by the text renderer, which makes `style={"initial_state": True}` a perfect trap: no error, no labels.

The deepest trap in this objective is confusing a rendering option with a semantic one. `reverse_bits` changes only which wire is drawn where; it does not change the circuit, the gate order, or the endianness of the counts you get back. Same for `idle_wires`: the qubit still exists, it is just not drawn.

Finally, conditionals. In Qiskit 2.x the only way to get a classically-controlled operation — and the boxed `If` block in the drawing that goes with it — is the control-flow context manager `with qc.if_test((clbit, value)):`. `InstructionSet.c_if` was removed in 2.0, there is no `condition=` gate keyword and no `.condition` attribute to set, and `if_test(clbit == 1)` fails because `Clbit.__eq__` returns a plain bool.

*Sources: [visualize-circuits](https://quantum.cloud.ibm.com/docs/guides/visualize-circuits) · [visualization](https://quantum.cloud.ibm.com/docs/api/qiskit/visualization) · [classical-feedforward-and-control-flow](https://quantum.cloud.ibm.com/docs/guides/classical-feedforward-and-control-flow)*

**Key facts:**

- `qc.draw()` returns a `TextDrawing` (not a `str`, not `None`); `qc.draw("mpl")` returns a `matplotlib.figure.Figure`. — ⚙️ proven in [`s2-q010`](/docs/sections/s2)
- The only valid `output` values are `text`, `latex`, `latex_source`, and `mpl` — `output="matplotlib"` (or `"figure"`) raises `VisualizationError` listing those four, from both the method and `circuit_drawer`. — ⚙️ proven in [`s2-q015`](/docs/sections/s2)
- The standalone drawer is `from qiskit.visualization import circuit_drawer` called as `circuit_drawer(qc, output="text")`; `qiskit.tools` no longer exists and the kwarg is `output=`, never `format=`. — ⚙️ proven in [`s2-q014`](/docs/sections/s2)
- `qc.draw("mpl", ax=...)` returns `None`, not a `Figure` — supplying your own axes hands figure ownership back to you. — ⚙️ proven in [`s2-q017`](/docs/sections/s2)
- `idle_wires=False` removes wires that carry no operations, so a 3-qubit circuit acting only on qubits 0 and 2 draws two wires. — ⚙️ proven in [`s2-q011`](/docs/sections/s2)
- `reverse_bits=True` is rendering-only: it puts the highest-index qubit on the top wire and changes nothing about the circuit, the gate order, or the endianness of the results. — ⚙️ proven in [`s2-q012`](/docs/sections/s2)
- `initial_state=True` (default `False`) prefixes each wire with its `|0⟩` label; the plural `initial_states=` is a `TypeError`, and `style={"initial_state": True}` is silently ignored by the text renderer. — ⚙️ proven in [`s2-q016`](/docs/sections/s2)
- A classically-controlled gate that draws as an `If` block is built with `with qc.if_test((qc.clbits[0], 1)):` — `.c_if()`, a `condition=` kwarg, a `.condition` attribute, and `if_test(clbit == 1)` all fail in Qiskit 2.x. — ⚙️ proven in [`s2-q013`](/docs/sections/s2)
- `reverse_bits` and `plot_barriers` are shared by all three renderers, while `fold`, `scale`, and `style` are renderer-specific, and `filename=` saves the rendering to disk. — 📖 [visualize-circuits](https://quantum.cloud.ibm.com/docs/guides/visualize-circuits)

## Visualize quantum measurements

### Counts in, Figure out — and the bar labels are little-endian

The measurement plotters take a counts *mapping* — bitstring to integer — and nothing else. A `SamplerV2` result does not hand you one directly: `result[0].data.meas` is a `BitArray`, and you must call `.get_counts()` on it. There is no bare `.counts()` method (that is an `AttributeError`), and passing the `BitArray` itself to `plot_histogram` fails. Both `plot_histogram` and `plot_distribution` return a `matplotlib.figure.Figure`, so `.savefig(...)` and `.show()` are always available on the result.

The pair differs in normalization, not in input. `plot_histogram` plots RAW counts: its y-axis is labeled *Count* and the bar heights add up to the number of shots. `plot_distribution` plots a normalized quasi-probability distribution: its y-axis is *Quasi-probability* and the heights add up to 1. It derives that normalization from the counts themselves — neither function has a `shots=` parameter, and passing one is a `TypeError`. The V1-era habit `plot_histogram(counts, shots=1024)` is simply gone.

The display options are a small, memorizable set: `legend` (a LIST of strings, one per execution — a bare string raises, and `labels=` does not exist), `sort` (`"asc"` or `"desc"`), `number_to_keep`, `color`, `bar_labels`, and `figsize`. Two of them carry traps. `number_to_keep=N` keeps the N largest-count bitstrings and folds every remaining outcome into one bar labeled `rest` whose height is the SUM of the folded counts, never their average and never a dropped remainder — no weight is lost. And overlaying two runs is done by passing a LIST of counts dicts as the single data argument, `plot_histogram([before, after], legend=["before", "after"])`; a dict-of-dicts or two positional arguments will not do it.

With no options at all, `plot_histogram` sorts the x-axis in ascending lexicographic bitstring order — not insertion order, not by bar height. So a dict built as `{"11": …, "00": …, "10": …, "01": …}` still draws as `00, 01, 10, 11`.

The last piece is reading the axis. Qiskit labels outcomes little-endian: the string is q_(n−1) … q_1 q_0, highest-index qubit on the LEFT and qubit 0 on the right. Flip qubits 0 and 2 of a three-qubit register and the single bar sits at `'101'`, not `'011'`. If the circuit has several classical registers (as it does after `measure_all`, which appends a fresh `meas` register), the key is space-separated, one group per register, the LAST-declared register printed leftmost. When a question asks "which bar is tallest", it is usually testing the label convention, not the physics — and when it does test physics, the shortcut is RY(θ)|0⟩ giving P(1) = sin²(θ/2).

*Sources: [visualize-results](https://quantum.cloud.ibm.com/docs/guides/visualize-results) · [visualization](https://quantum.cloud.ibm.com/docs/api/qiskit/visualization)*

**Key facts:**

- `plot_histogram` plots RAW counts (bar heights sum to the shot count, y-axis "Count"); `plot_distribution` normalizes (heights sum to 1.0, y-axis "Quasi-probability"). Both accept the same counts dict. — ⚙️ proven in [`s2-q020`](/docs/sections/s2)
- Neither plotter has a `shots=` parameter — `plot_distribution(counts, shots=1024)` raises `TypeError`; normalization is derived from the counts themselves. — ⚙️ proven in [`s2-q020`](/docs/sections/s2)
- `number_to_keep=2` on four outcomes draws three bars — the two largest plus `rest`, whose height is the SUM of the folded counts (20 + 4 → 24), never their average. — ⚙️ proven in [`s2-q021`](/docs/sections/s2)
- With no options, `plot_histogram` sorts bars in ascending bitstring order regardless of insertion order or height, and returns a `Figure`. — ⚙️ proven in [`s2-q025`](/docs/sections/s2)
- Overlaying runs takes a LIST of counts dicts plus a matching list `legend`: `plot_histogram([before, after], legend=["before", "after"])`. `labels=` does not exist and a bare string legend raises. — ⚙️ proven in [`s2-q023`](/docs/sections/s2)
- `SamplerV2` output must be converted first: `result[0].data.meas.get_counts()`. The `BitArray` itself is not a counts mapping and has no bare `.counts()` method. — ⚙️ proven in [`s2-q022`](/docs/sections/s2)
- Histogram labels are little-endian q_(n−1)…q_0: flipping qubits 0 and 2 of a 3-qubit register puts the single bar at `'101'`, not `'011'`. — ⚙️ proven in [`s2-q019`](/docs/sections/s2)
- The documented `plot_histogram` options are `legend`, `sort` (`asc`/`desc`), `number_to_keep`, `color`, `bar_labels`, and `figsize` — and the function returns a `matplotlib.Figure`. — 📖 [visualize-results](https://quantum.cloud.ibm.com/docs/guides/visualize-results)
- `plot_gate_map(backend)` is a picture of the HARDWARE: it takes a `BackendV2`, reads its qubit count and coupling map, and draws one node per qubit plus one line per connected pair. A counts mapping, a `CouplingMap` or a `Target` all raise `AttributeError` — and `plot_histogram(backend)` raises too. — ⚙️ proven in [`s2-q037`](/docs/sections/s2)
- The three device plots draw the same qubit graph and differ only in what they colour: `plot_error_map(backend)` shades every qubit and every link from the backend's calibration data, `plot_circuit_layout(isa, backend)` uses a two-tone used/unused highlight labelled with virtual indices, and `plot_gate_map` forwards no colours at all (`plot_directed=True` adds arrows, not error data). — ⚙️ proven in [`s2-q038`](/docs/sections/s2)
- `plot_circuit_layout` reads `circuit.layout`, which only the circuit RETURNED by `transpile` carries — `transpile` never mutates its input, so plotting the original circuit raises `QiskitError: 'Circuit has no layout. Perhaps it has not been transpiled.'` at every optimization level. — ⚙️ proven in [`s2-q036`](/docs/sections/s2)
- `Statevector.sample_counts(shots)` returns a `qiskit.result.Counts` mapping — bitstring labels to integers that sum to `shots`, with only the nonzero-amplitude outcomes present — so it feeds `plot_histogram` with no backend or primitive involved. `sample_memory(shots)` is the per-shot list, `probabilities_dict()` the exact probabilities, and `sv.seed(...)` makes the draw reproducible. — ⚙️ proven in [`s2-q039`](/docs/sections/s2)

## Visualize quantum states

### Each state plot answers a different question

Four drawers, four different questions, and the exam mostly tests which one you would reach for and what it can*not* show. Every one of them is reachable two ways: the free function (`plot_bloch_multivector`, `plot_state_qsphere`, `plot_state_city`, `plot_state_hinton`, `plot_state_paulivec`) or the object method `sv.draw(output)` where `output` is the first positional parameter and takes `'text'`, `'latex'`, `'latex_source'`, `'qsphere'`, `'hinton'`, `'bloch'`, `'city'` or `'paulivec'` — any other token raises `ValueError` listing exactly those. There is no `sv.plot(...)` and no importable `plot_qsphere`.

**Bloch.** Two functions whose names look interchangeable and are not. `plot_bloch_vector` takes an explicit three-number Bloch vector `[x, y, z]`; `plot_bloch_multivector` takes a quantum STATE (`Statevector` or `DensityMatrix`), computes each qubit's reduced state by tracing out the others, and draws one sphere per qubit — three qubits, three spheres, all packed into one `Figure`, idle qubits included. Feeding a state to `plot_bloch_vector` does not produce per-qubit spheres, and feeding a list of Bloch vectors to the multivector version raises (it is parsed as a state). Because it only ever shows single-qubit expectation values, this plot cannot represent correlations: for a Bell pair each reduced state is maximally mixed, so both arrows shrink to zero length at the centre. Arrows at the origin ARE the visual signature of maximal entanglement.

The Bloch vector is (⟨X⟩, ⟨Y⟩, ⟨Z⟩), so reading an arrow is memorization: +Z = |0⟩, −Z = |1⟩, +X = |+⟩, −X = |−⟩, +Y = (|0⟩ + i|1⟩)/√2 (the label `'r'`), −Y = (|0⟩ − i|1⟩)/√2 (`'l'`). Equator means ⟨Z⟩ = 0. H alone lands on +X; H then S rotates 90° about Z to +Y; and the classic decoy is RZ on |0⟩, which changes only a global phase and leaves the arrow pinned at the north pole.

**Q-sphere.** One node per computational basis state with NONZERO amplitude — zero-amplitude states simply have no marker. Node SIZE encodes the amplitude magnitude and node COLOR encodes its complex phase. Two same-size, different-color nodes therefore mean equal weight but a relative phase (a −1 amplitude shows as phase π against phase 0). Unlike the other state plots it accepts only `figsize`, not `title`.

**City / Hinton / Pauli-vector.** These render the density matrix rather than the qubits: `plot_state_city` as two 3-D bar charts (real and imaginary parts), `plot_state_hinton` as squares whose size is the magnitude, `plot_state_paulivec` as the expansion coefficients over Pauli strings. Reach for them when a question is about matrix elements or Pauli decompositions instead of per-qubit directions.

*Sources: [plot-quantum-states](https://quantum.cloud.ibm.com/docs/guides/plot-quantum-states) · [visualization](https://quantum.cloud.ibm.com/docs/api/qiskit/visualization)*

**Key facts:**

- `plot_bloch_multivector` draws one sphere PER QUBIT (3 qubits → 3 spheres, idle ones included) from each qubit's reduced state, and returns a single `Figure`. — ⚙️ proven in [`s2-q026`](/docs/sections/s2)
- `plot_bloch_vector` takes an explicit `[x, y, z]` Bloch vector; `plot_bloch_multivector` takes a quantum state. Passing a state to the former does not produce per-qubit spheres. — ⚙️ proven in [`s2-q034`](/docs/sections/s2)
- For the Bell state both reduced Bloch vectors are exactly (0, 0, 0) with purity 0.5 — the arrows collapse to the centre, the visual signature of maximal entanglement. — ⚙️ proven in [`s2-q030`](/docs/sections/s2)
- `sv.draw("qsphere")` works (`output` is the first positional parameter); the valid tokens are `text`, `latex`, `latex_source`, `qsphere`, `hinton`, `bloch`, `city`, `paulivec`. `sv.qsphere()`, `sv.plot(...)` and importing `plot_qsphere` all fail. — ⚙️ proven in [`s2-q029`](/docs/sections/s2)
- On a q-sphere, node SIZE encodes amplitude magnitude and node COLOR encodes phase: two equal-magnitude amplitudes of +0.7071 and −0.7071 give same-size nodes at phase 0 and phase π, hence different colors. — ⚙️ proven in [`s2-q032`](/docs/sections/s2)
- A q-sphere shows a node only where the amplitude is nonzero — H on qubit 0 with X on qubit 1 gives nodes at `|10⟩` and `|11⟩` only (little-endian labels). — ⚙️ proven in [`s2-q031`](/docs/sections/s2)
- H then S puts the arrow on +Y, i.e. (|0⟩ + i|1⟩)/√2 with Bloch vector (0, 1, 0); H alone gives +X. — ⚙️ proven in [`s2-q027`](/docs/sections/s2)
- The Bloch vector is (⟨X⟩, ⟨Y⟩, ⟨Z⟩), so an arrow on −X is |−⟩ = (|0⟩ − |1⟩)/√2 — the −1 eigenstate of X. — ⚙️ proven in [`s2-q028`](/docs/sections/s2)
- Equator means ⟨Z⟩ = 0: `h` and `h; s` both land there, while `rz(π/2)` on |0⟩ only adds a global phase and stays at the north pole. — ⚙️ proven in [`s2-q035`](/docs/sections/s2)
