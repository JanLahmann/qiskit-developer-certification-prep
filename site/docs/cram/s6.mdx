## Set estimator primitive options such as resilience levels

### The resilience_level dial: what levels 0, 1 and 2 actually buy

`resilience_level` is a single coarse dial that abstracts away the detailed choice of noise-management method so you can reason about the cost/accuracy trade instead. The official table has exactly three rows. Level 0 applies NO mitigation. Level 1 — the default — is the minimal-cost tier: it mitigates readout error via Twirled Readout Error eXtinction (TREX), which is measurement twirling plus an inversion of the diagonalized readout-error transfer matrix. Level 2 is 'medium mitigation costs': everything level 1 does, PLUS zero-noise extrapolation and gate twirling; the docs describe it as typically reducing bias 'but not guaranteed to be zero-bias'. There is no level 3, and no level turns on PEC — probabilistic error cancellation exists only as the individual option `resilience.pec_mitigation`.

The direction of the trade is fixed and is the single most-tested consequence: higher levels build MORE resilience by running and post-processing a larger ensemble of related circuits, so they give more accurate (less biased) expectation values at the cost of longer processing time and more QPU usage. Nothing about a higher level makes a job cheaper, faster, shallower, or shot-thriftier, and no level changes which physical qubits you land on.

The second consequence is the override rule, and it is stated as an 'Important' callout in the noise-management guide: any option you specify yourself is applied IN ADDITION TO the base set of options the resilience level defines. So you may set level 1 and then switch measurement mitigation back off (inadvisable, but legal), and — read the other way — setting level 0 turns `zne_mitigation` off, yet an explicit `estimator.options.resilience.zne_mitigation = True` overrides that and re-enables ZNE. A level is a starting point, never a lock.

Keep the mitigation/suppression split straight, because the exam leans on it. Error SUPPRESSION acts before or during execution to stop errors happening: dynamical decoupling inserts pulse sequences on idling qubits so their idle-time errors approximately cancel, and it is enabled through `options.dynamical_decoupling.enable`, not through any resilience level. Error MITIGATION runs an ensemble of related circuits and post-processes the outputs to remove bias from expectation values: TREX, ZNE, PEA and PEC. Raising the transpiler's optimization level or simply buying more shots is neither — more shots shrink the STATISTICAL error, while mitigation attacks the systematic bias.

One library detail worth carrying: the validator accepts only the integers 0, 1 and 2. `3`, `4`, `5` and `-1` raise a range error and `1.5` and `None` are rejected outright (a string `"2"` or `2.0` is silently coerced, so never treat those as errors).

### The EstimatorOptions tree: which knob lives at which level

`EstimatorOptions` is a nested dataclass, and most option questions are really questions about the nesting depth. The top level holds `max_execution_time`, `environment`, `simulator`, `default_precision`, `default_shots`, `resilience_level`, `seed_estimator`, `dynamical_decoupling`, `resilience`, `execution`, `twirling` and `experimental`. The resilience group holds `measure_mitigation`, `measure_noise_learning`, `zne_mitigation`, `zne`, `pec_mitigation`, `pec`, `layer_noise_learning` and `layer_noise_model`. One level deeper, `resilience.zne` holds exactly four fields: `amplifier`, `noise_factors`, `extrapolator` and `extrapolated_noise_factors`.

That shape produces three classic traps. First, WRONG NAME: `zne.factors` and the Mitiq-flavoured `zne.scale_factors` do not exist. Second, WRONG LEVEL: `resilience.noise_factors` is the right word at the wrong depth, and a top-level `options.zne_mitigation` is likewise no such attribute — both raise pydantic validation errors. Third, and nastiest, CONFIGURING IS NOT ENABLING: setting `resilience.zne.noise_factors = [1, 3, 5, 7]` is accepted and leaves `zne_mitigation` at `Unset`, so the job still runs without ZNE. Worse, `resilience.zne_mitigation.enable = True` raises nothing at all — `Unset` is a plain singleton, so the attribute write lands harmlessly on it and ZNE stays off. Only `resilience.zne_mitigation = True` (or `resilience_level = 2`) actually turns it on; symmetrically, TREX is `resilience.measure_mitigation = True` and PEC is `resilience.pec_mitigation = True`.

Memorize the documented defaults, since 'what happens if I touch nothing' is a question shape: `resilience_level` 1, `resilience.measure_mitigation` True, `zne_mitigation` False, `pec_mitigation` False, `zne.noise_factors` (1, 3, 5), `zne.amplifier` `gate_folding`, `zne.extrapolator` (exponential, linear), `dynamical_decoupling.enable` False with `sequence_type` XX, `twirling.enable_gates` False but `twirling.enable_measure` True, `default_precision` 0.015625 — which is exactly 1/sqrt(4096) — and `max_execution_time` 10800 seconds. Any option you never touch sits at the special value `Unset`, meaning the server default applies.

Setting works three ways: pass an `EstimatorOptions` instance or a plain nested dict at construction, assign down the attribute path afterwards (`estimator.options.resilience.zne.noise_factors = [1, 3, 5]`), or call `options.update(...)` for a bulk edit. The constructor is not a loophole for invalid values: `default_precision = 0` fails identically whether you assign it, pass it in a dict, or build `EstimatorOptions(default_precision=0)`, because it is the same 'must be &gt; 0' validator. Finally, some techniques exclude each other — the feature-compatibility table lists PEC as incompatible with gate-folding ZNE and with PEA, and the library enforces it: enabling `pec_mitigation` and `zne_mitigation` together raises a validation error.

## Understand the theoretical background behind the estimator primitive

### The Estimator PUB: four slots, and the broadcasting that fixes the output shape

An Estimator PUB is a tuple of AT MOST FOUR values, in this order: (1) a single `QuantumCircuit`, which may contain `Parameter` objects; (2) an array of one or more observables — anything `ObservablesArrayLike`: `Pauli`, `SparsePauliOp`, `PauliList` or a bare string; (3) a collection of parameter values to bind, whose LAST index runs over the circuit's parameters, omitted or `None` if the circuit has none; (4) optionally a target precision. The slots are positional, never searched by content, which is why dropping a float into the third slot produces the cryptic `ValueError: Length of () inconsistent with last dimension of [0.01]` — the estimator tried to read your precision as a parameter binding. And a single task still has to be wrapped in a list: `est.run([(isa, iobs)])`, not `est.run((isa, iobs))`.

The output shape is decided entirely by NumPy broadcasting between the observables array and the parameter-value array, and the Estimator returns one expectation value per element of the broadcast shape. Four patterns cover almost every question. One observable, no parameters: `evs` is a 0-d array (shape `()`). A flat Python list of three observables: shape `(3,)`. The same three written as a column, `[[o1], [o2], [o3]]`: shape `(3, 1)`. Written as a row, `[[o1, o2, o3]]`: shape `(1, 3)`. Parameters broadcast the same way — a `(4, 1)` parameter array against one observable gives `(4,)`, and a `(1, 6)` parameter set against a `(4, 1)` observable column gives the outer product `(4, 6)`.

The rule that catches people: a `SparsePauliOp` counts as a SINGLE element no matter how many Pauli terms it contains. `SparsePauliOp.from_list(['XX', 'XY', 'IZ'])` has shape `()` and returns ONE number — the coefficient-weighted sum of its terms — whereas `[SparsePauliOp('XX'), SparsePauliOp('XY'), SparsePauliOp('IZ')]` has shape `(3,)` and returns three. There is no per-term breakdown, ever. One related planning note: commuting observables share a single measurement only if they are grouped in the SAME PUB; two PUBs over the same circuit are two different measurement bases and cost two sets of circuits.

What comes back is a `PrimitiveResult` holding one `PubResult` per PUB. `result[0].data` is a `DataBin` whose keys are exactly `evs` and `stds` — the estimates and their standard errors, both real `float64` even though `SparsePauliOp.coeffs` are complex. There is no `expectation_values` field, no `variance`, and `PubResult.metadata` carries only run bookkeeping (`target_precision`, `circuit_metadata`), never the numbers themselves.

### Observables, layout alignment, and the precision-to-shots law

To measure an n-qubit observable on hardware you must write it as a weighted sum of tensor products of Paulis — that is what `SparsePauliOp` stores. Three constructors, three different signatures. The plain constructor takes labels plus `coeffs` and infers the width from the labels: `SparsePauliOp(['ZZ', 'XX'], coeffs=[1.0, 0.5])`. `from_list` takes (label, coefficient) pairs on FULL-WIDTH labels. `from_sparse_list` takes (label, qubit_indices, coefficient) triples plus `num_qubits`, which is a REQUIRED argument there and a `TypeError` if omitted — and it pads the result with identities, so `[('Z', [0], 1.0)]` at `num_qubits=3` stores `'IIZ'`, never a bare `'Z'`. Mixing widths inside one call raises `ValueError: The Nth Pauli is defined over k qubits`, and the plain constructor has no `num_qubits=` keyword at all. Note that only I/Z Paulis are diagonal in the measurement basis; X and Y terms require a basis change (H for X, S-dagger then H for Y), which the Estimator performs for you automatically.

Then comes the step that generates more Estimator bugs than anything else. Transpiling maps your logical qubits onto physical ones and pads the circuit out to the backend's full width, possibly permuting them. Your observable does not follow along. Submit a 2-qubit `SparsePauliOp` with a 5-qubit ISA circuit and the run dies with `ValueError: The number of qubits of the circuit (5) does not match the number of qubits of the ()-th observable (2)`. The fix is `isa_observable = observable.apply_layout(isa_circuit.layout)`, which expands AND permutes the observable onto the same physical qubits. Nothing else rescues it: adding `measure_all()`, passing the observable as a string, or pinning `initial_layout=[0, 1]` all leave the ISA circuit at full backend width. You can also align by hand with an explicit index list plus a width — `SparsePauliOp('ZZ').apply_layout([2, 0], num_qubits=4)` yields `'IZIZ'`, the label characters pairing with the index list left-to-right while the printed label stays little-endian (rightmost character = qubit 0).

Finally, precision. `precision` is a target STANDARD ERROR on the expectation value, not a shot count — which is why it is a float and why `default_precision = 0` is rejected as non-positive. Statistical error falls as 1/sqrt(N), so the shot cost goes as 1/precision^2: halving the target precision quadruples the shots, and a doubling or a 1.4x bump does not get you there. The documented default 0.015625 is literally 1/sqrt(4096). Where the value comes from follows a strict precedence: a precision inside the PUB wins, then `run(precision=...)`, then (twirling being on by default) the product of `num_randomizations` and `shots_per_randomization`, then `default_shots`, then `default_precision`. Two guardrails: the result is not GUARANTEED to reach the requested precision, and lower precision means more QPU time.

**Key facts:**

- `result[0].data.evs` holds the estimate(s) and `result[0].data.stds` their standard errors; `data.expectation_values` is an `AttributeError` and `metadata['evs']` a `KeyError`. — ⚙️ proven in [`s6-q010`](/docs/sections/s6)
- PUB slots are positional — (circuit, observables, parameter_values, precision). A float in the third slot raises `ValueError: Length of () inconsistent with last dimension of [0.01]`; moving it to the fourth slot runs cleanly. — ⚙️ proven in [`s6-q025`](/docs/sections/s6)
- Even a single task must be wrapped in a list: `est.run([(isa, iobs)])`. A bare circuit raises `ValueError: An invalid Estimator pub-like was given`, and `run(circuits=..., observables=...)` is a V1 habit that raises `TypeError`. — ⚙️ proven in [`s6-q012`](/docs/sections/s6)
- Width mismatch is the signature Estimator bug: a 2-qubit observable against a 5-qubit ISA circuit raises `ValueError: The number of qubits of the circuit (5) does not match the number of qubits of the ()-th observable (2)`; only `obs.apply_layout(isa.layout)` fixes it (pinning `initial_layout` does not). — ⚙️ proven in [`s6-q013`](/docs/sections/s6)
- `SparsePauliOp('ZZ').apply_layout([2, 0], num_qubits=4)` returns `'IZIZ'` — label characters pair with the index list left-to-right while the printed label stays little-endian. — ⚙️ proven in [`s6-q033`](/docs/sections/s6)
- `SparsePauliOp.from_sparse_list([('Z', [0], 1.0)], num_qubits=3)` pads with identities to `'IIZ'` — it never raises and never leaves a bare `'Z'`. — ⚙️ proven in [`s6-q035`](/docs/sections/s6)
- `SparsePauliOp.from_list([('ZZ', 1.0), ('XX', 0.5)])` is the valid two-qubit build; mixing label widths raises `ValueError: The 1th Pauli is defined over 1 qubits`, and `from_sparse_list` without `num_qubits` is a `TypeError` (it is required there). — ⚙️ proven in [`s6-q024`](/docs/sections/s6)
- One PUB with a flat Python list of three observables returns `evs` of shape `(3,)` — not `(3, 1)`, not `(1, 3)`, and not `(3, 2)`. — ⚙️ proven in [`s6-q030`](/docs/sections/s6)
- Two observables `['ZI', 'IZ']` on a circuit with X on qubit 0 broadcast to `[1.0, -1.0]` of shape `(2,)`: the little-endian label rule decides which value is which, and the observables are broadcast, never summed. — ⚙️ proven in [`s6-q015`](/docs/sections/s6)
- A multi-term `SparsePauliOp` is ONE observable: `from_list([('X', 3.0)])` on |+⟩ returns a 0-d `float64` array holding 3.0 — never a length-1 array, never one value per Pauli term, never a complex number. — ⚙️ proven in [`s6-q022`](/docs/sections/s6)
- Coefficients are contracted before you see them: 0.5·ZZ + 0.5·XX on a Bell state comes back as the single scalar 1.0. — ⚙️ proven in [`s6-q011`](/docs/sections/s6)
- Binding one parameter to `[0, π/2, π]` against a single observable gives `evs` of shape `(3,)` equal to `[1.0, 0.0, -1.0]` — the ⟨Z⟩ = cos θ curve, one flat value per parameter set. — ⚙️ proven in [`s6-q023`](/docs/sections/s6)
- Halving the target precision quadruples the shot budget: the measured standard error falls from 0.0195 at the baseline 2500 shots to 0.0104 at 4x the shots, while 2x only reaches 0.0137 (a sqrt law would have predicted ~1.4x). — ⚙️ proven in [`s6-q017`](/docs/sections/s6)
- The reference `StatevectorEstimator` reports `stds` of exactly `0.0` — an exact calculation has no sampling uncertainty — and it stays 0.0 even when `run()` is asked for a tighter precision. — ⚙️ proven in [`s6-q037`](/docs/sections/s6)
- An Estimator PUB holds at most four values (circuit, observables array, parameter values, optional target precision), and the Estimator returns one expectation value per element of the broadcast shape. — 📖 [primitive-input-output](https://quantum.cloud.ibm.com/docs/guides/primitive-input-output)
- Each `SparsePauliOp` counts as a single element for broadcasting: `SparsePauliOp.from_list(['XX', 'XY', 'IZ'])` has shape `()`, while the same three ops in a Python list have shape `(3,)`. — 📖 [primitive-input-output](https://quantum.cloud.ibm.com/docs/guides/primitive-input-output)
- Commuting observables are only estimated from the SAME measurement when they are grouped in one PUB; the same circuit in two PUBs means two measurement bases and two sets of circuits. — 📖 [primitive-input-output](https://quantum.cloud.ibm.com/docs/guides/primitive-input-output)
- Precision precedence, highest first: a precision inside the PUB, then `run(precision=...)`, then twirling's `num_randomizations` × `shots_per_randomization`, then `default_shots`, then `default_precision` (documented default 0.015625 = 1/sqrt(4096)). — 📖 [estimator-options](https://quantum.cloud.ibm.com/docs/guides/estimator-options)
- Only Paulis built from I and Z are diagonal in the measurement basis; X and Y terms need a basis change (H for X, S-dagger then H for Y), which the Estimator performs automatically. — 📖 [specify-observables-pauli](https://quantum.cloud.ibm.com/docs/guides/specify-observables-pauli)
