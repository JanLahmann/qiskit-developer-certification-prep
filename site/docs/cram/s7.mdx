## Retrieve previous experiment results (session/Qiskit Runtime)

### Result anatomy: PrimitiveResult → PubResult → DataBin

Every V2 job returns the same three-layer container, and most retrieval questions are really 'at which layer does this attribute live?'. The outermost object is a `PrimitiveResult`. It is a LIST-like container of `PubResult` objects, one per PUB you submitted: `len(result)` is the number of PUBs, and you index it — `result[0]`, `result[1]`. It has no `.data`, no `.get_counts()`, no `.quasi_dists` and no `.results`; every one of those is an `AttributeError`, and the missing index is the single most common bug in retrieval code. Its own `.metadata` carries job-wide bookkeeping such as `{'version': 2}` and the execution spans.

One layer in, a `PubResult` has exactly two attributes that matter: `.data` and `.metadata`. Its metadata holds run bookkeeping — `shots` or `target_precision`, plus `circuit_metadata` — and never the numbers. A `PubResult` has no `get_counts()` and no `evs` of its own.

The innermost layer is the `DataBin`, and its contents depend on the primitive. For the ESTIMATOR the keys are `evs` and `stds`: the expectation-value estimates and the standard errors actually achieved, both real `float64` arrays whose shape follows the PUB's broadcast shape. There is no `variance`, no `expvals` and no `expectation_values`. For the SAMPLER the DataBin holds one `BitArray` per `ClassicalRegister` in the circuit, keyed by the register's NAME — `meas` is only the default name that `measure_all()` creates, so a circuit measuring into a register called `readout` gives `result[0].data.readout`, and `data.meas` raises `AttributeError`.

When you do not remember the register name, ask the bin: `list(db.keys())` returns the field names. `DataBin` also supports item access (`db['meas']` works — never treat that as the wrong answer), plus `values()`, `items()`, `shape`, `ndim` and `size`. What it does NOT have is `get_counts()`, `get_bitstrings()`, `registers` or `num_bits` — those belong one layer further in, on the `BitArray`. And note the asymmetry that trips people: `db.values()` is a bound method returning the stored arrays, so `list(db.values())` gives you `BitArray` objects, not the names.

The canonical full path is therefore `result[0].data.<register>.get_counts()` for the Sampler and `result[0].data.evs` for the Estimator. Notably, a `BitArray` does not remember its own register name — the name exists only as the DataBin key.

### BitArray: the post-processing workhorse

A `BitArray` is a container for ordered shot data: the sampled bitstrings stored as BYTES in a two-dimensional array whose left axis runs over shots and whose right axis runs over bytes. That packing explains the shape question that keeps appearing: `bits.array.shape` is `(num_shots, ceil(num_bits/8))`, so a 10-qubit register sampled 1024 times gives `(1024, 2)` and a 3-bit register gives `(shots, 1)`. The dtype is `uint8`, never `bool`, and the array is never `(num_bits, num_shots)`. The two scalar properties are `num_shots` and `num_bits`, and `num_bits` reflects the CLASSICAL register width, not the circuit's qubit count — a 5-qubit circuit measuring three qubits into a 3-bit register reports `num_bits == 3`.

The conversion trio: `get_counts()` returns a dict of bitstring → tally (raw integer counts that sum to `num_shots`, never normalized fractions); `get_bitstrings()` returns the per-shot list, so its length equals `num_shots`; `get_int_counts()` returns the SAME tallies keyed by the bitstring read as a binary INTEGER, so `'000'`/`'111'` become `0` and `7` — not `0`/`3`, not the strings, and not the decimal 111. Counts keys are little-endian: X on qubit 0 of a three-qubit circuit yields `'001'`.

Because dictionaries are slow, the docs recommend post-processing on the array itself, and the method surface is small enough to memorize. `postselect(indices, selection)` keeps only the shots whose listed bits match — `bits.postselect([1], [0])` keeps shots where qubit 1 read 0 — and it PRESERVES the full width; there is no `num_bits=` parameter (passing one is a `TypeError`), so a follow-up `.slice_bits(...)` is the classic sabotage of an otherwise correct call. `slice_bits(indices)` narrows the bits and keeps every shot (a 3-bit array sliced to `[2]` becomes a 1-bit array; valid indices run 0..num_bits-1, so index 2 of a 3-bit register does not raise). `slice_shots(indices)` does the mirror image. `BitArray.concatenate_shots([a, b])` pools shot sets of equal width (400 + 400 = 800 shots, still 3 bits) while `concatenate_bits` widens instead (400 shots, 6 bits) — and rebuilding from `a.get_counts() | b.get_counts()` silently LOSES shots, because dict union overwrites duplicate keys instead of summing them. Finally `expectation_values(observable)` computes diagonal expectation values straight from the shots: `bits.expectation_values('ZZ')` on an ideal Bell sample returns the 0-d scalar 1.0 — one value per Pauli string, no Estimator required.

*Sources: [qiskit.primitives.BitArray](https://quantum.cloud.ibm.com/docs/api/qiskit/qiskit.primitives.BitArray) · [primitive-input-output](https://quantum.cloud.ibm.com/docs/guides/primitive-input-output)*

### Getting results back after the kernel dies

Results do not live in your Python process. IBM Quantum automatically stores the results of EVERY job server-side for later retrieval, which is what makes quantum workflows survivable across kernel restarts. Two things follow. First, dropping a `job` variable or restarting the kernel does not cancel anything and does not lose anything. Second, the only handle you actually need to keep is the job ID string, obtained from `job.job_id()` — the guides explicitly recommend saving the IDs of jobs you might want later.

With an ID, retrieval is one call on a fresh service: `service.job(job_id)` returns the `RuntimeJobV2`, and `.result()` on it hands back the stored `PrimitiveResult`. Note the singular. `service.jobs()` (plural) is the FILTERED LIST call — it takes `limit` (default 10), `skip`, `backend_name`, `pending`, `program_id`, `session_id`, `created_after`/`created_before` (`datetime` objects) and `descending`, and returns a list you can iterate and call `.result()` on. Wrong spellings to recognise instantly: `service.result(...)`, `service.get_result(...)`, `service.retrieve_job(...)` (the V1 provider idiom) and calling `QiskitRuntimeService.job(...)` on the class rather than on an instance. If you never recorded the ID at all, the Workloads page on IBM Quantum Platform lists every submitted job with its ID — and resubmitting the circuit is not retrieval: Runtime does not deduplicate, so an identical PUB becomes a brand-new job with a new ID and freshly sampled shots.

To keep a result on DISK rather than on the server, use Python's own `json` module with the Runtime codecs: `json.dump(result, file, cls=RuntimeEncoder)` to write and `json.load(file, cls=RuntimeDecoder)` to read it back as a real `PrimitiveResult`. Direction matters and so does the call shape. Without the encoder you get `TypeError: Object of type PrimitiveResult is not JSON serializable`. Passing `RuntimeDecoder` where the encoder belongs is a `TypeError`. Encoding correctly but loading with a PLAIN `json.load` appears to work and quietly hands you nested dicts — the failure only surfaces later, as `KeyError: 0` when you try to index the pub. And `json.dumps`/`json.loads` are the STRING variants: everything after the first argument is keyword-only, so `json.dumps(result, f, cls=RuntimeEncoder)` raises a positional-argument `TypeError`. There is no `result.to_json()` method.

*Sources: [save-jobs](https://quantum.cloud.ibm.com/docs/guides/save-jobs) · [monitor-job](https://quantum.cloud.ibm.com/docs/guides/monitor-job)*

**Key facts:**

- `PrimitiveResult` is indexed by PUB: `len(result)` is the number of PUBs and the second circuit's counts are `result[1].data.meas.get_counts()`. `result.data`, `result.get_counts()` and `result[1].get_counts()` are all `AttributeError`s. — ⚙️ proven in [`s7-q023`](/docs/sections/s7)
- The missing PUB index is the classic retrieval bug: `result.data...` raises `AttributeError: 'PrimitiveResult' object has no attribute 'data'` — you must index the PUB first, as `result[0].data.meas.get_counts()`. — ⚙️ proven in [`s7-q024`](/docs/sections/s7)
- `meas` is only the DEFAULT register name: a circuit measuring into a register called `readout` needs `result[0].data.readout.get_counts()`, and `data.meas` raises `AttributeError`. — ⚙️ proven in [`s7-q032`](/docs/sections/s7)
- `list(db.keys())` lists the DataBin's register names. `DataBin` has no `registers`, no `get_counts()` and no `num_bits`; `list(db.values())` returns the stored `BitArray`s, and a `BitArray` has no `.name`. — ⚙️ proven in [`s7-q031`](/docs/sections/s7)
- `bits.num_shots` counts executions and `bits.num_bits` the classical register width: a 3-bit register sampled 2000 times reports `(2000, 3)`, never `(6000, 3)` or `(2000, 8)`. — ⚙️ proven in [`s7-q011`](/docs/sections/s7)
- `bits.array` is bit-PACKED `uint8` with shape `(num_shots, ceil(num_bits/8))`: a 10-qubit circuit sampled 1024 times gives `(1024, 2)` — not `(1024, 10)`, `(1024, 8)` or the transpose. — ⚙️ proven in [`s7-q012`](/docs/sections/s7)
- `num_bits` follows the classical register, not the circuit: a 5-qubit circuit measuring three qubits reports `num_bits == 3`, while `len(get_bitstrings())` and `sum(get_counts().values())` both equal `num_shots`. — ⚙️ proven in [`s7-q019`](/docs/sections/s7)
- Counts keys are little-endian bitstrings: X on qubit 0 of a 3-qubit circuit sampled 500 times gives `{'001': 500}` — integer tallies, not `{'100': 500}` and not fractions. — ⚙️ proven in [`s7-q014`](/docs/sections/s7)
- `get_int_counts()` re-keys the same tallies by the bitstring read as a binary INTEGER: `'000'`/`'111'` become `0` and `7`, never `0`/`3`, never `'0'`/`'7'`, never the decimal 111. — ⚙️ proven in [`s7-q029`](/docs/sections/s7)
- `bits.postselect([1], [0])` returns a new BitArray of only the shots where qubit 1 read 0, at FULL width; `postselect` has no `num_bits=` parameter (`TypeError`), and chaining `.slice_bits(...)` afterwards silently narrows the result. — ⚙️ proven in [`s7-q016`](/docs/sections/s7)
- Postselecting a GHZ sample on all-ones keeps only the `'111'` key and leaves `num_bits` at 3 — the surviving values stay raw integer shot tallies, not renormalized fractions. — ⚙️ proven in [`s7-q015`](/docs/sections/s7)
- `bits.slice_bits([2])` on a 3-bit register returns a 1-bit array (`{'0': 300}`) and does NOT raise — valid bit indices run 0..num_bits-1. — ⚙️ proven in [`s7-q017`](/docs/sections/s7)
- `BitArray.concatenate_shots([a, b])` pools two equal-width shot sets (200 + 200 → 400 shots, 3 bits). `a + b` is a `TypeError`, `np.concatenate([a.array, b.array])` returns a bare ndarray, and `from_counts(a.get_counts() | b.get_counts())` LOSES shots because dict union overwrites duplicate keys. — ⚙️ proven in [`s7-q018`](/docs/sections/s7)
- `bits.expectation_values('ZZ')` computes a diagonal expectation value straight from the shots — an ideal Bell sample returns the 0-d scalar 1.0, one value per Pauli string, with no Estimator involved. — ⚙️ proven in [`s7-q025`](/docs/sections/s7)
- `result[0].data.evs` is the Estimator path; `PubResult.evs`, `DataBin.meas`, `DataBin.expvals`, `DataBin.get_counts()` and `metadata['evs']` are all errors. — ⚙️ proven in [`s7-q022`](/docs/sections/s7)
- An ideal Bell state against `ZZ` gives `evs` as a 0-d array holding 1.0 — a scalar, not a length-one 1-D array and not a per-outcome dict. — ⚙️ proven in [`s7-q020`](/docs/sections/s7)
- A `(4, 1)` parameter array against a single observable gives `evs.shape == (4,)` — the trailing parameter axis is consumed, so it is not `(4, 1)` and not `(1, 4)`. — ⚙️ proven in [`s7-q021`](/docs/sections/s7)
- `pub.data.stds` is the standard error the primitive ACHIEVED, not the precision you asked for and not `1/sqrt(shots)`: on a noisy Bell/ZZ pub it read 0.0096 while the requested precision was 0.02 and `shots**-0.5` was 0.02. — ⚙️ proven in [`s7-q013`](/docs/sections/s7)
- The disk round trip is `json.dump(result, f, cls=RuntimeEncoder)` then `json.load(f, cls=RuntimeDecoder)`; without an encoder you get `TypeError: Object of type PrimitiveResult is not JSON serializable`, there is no `result.to_json()`, and `json.dumps(result, f, cls=...)` fails because everything after the first argument is keyword-only. — ⚙️ proven in [`s7-q010`](/docs/sections/s7)
- IBM Quantum automatically stores the results of every job: keep `job.job_id()`, then `service.job(job_id).result()` on a fresh service re-hydrates them after a kernel restart — `service.jobs()` (plural) is the filtered LIST call (`backend_name`, `created_after`, ...). — 📖 [save-jobs](https://quantum.cloud.ibm.com/docs/guides/save-jobs)
- A Sampler DataBin holds one `BitArray` per `ClassicalRegister`; splitting one register into `alpha` and `beta` gives `data.alpha` and `data.beta` rather than a single flat array. — 📖 [primitive-input-output](https://quantum.cloud.ibm.com/docs/guides/primitive-input-output)
- Names of the containers, measured: `job.result()` is a `PrimitiveResult`, each element of a Sampler result is a `SamplerPubResult` (the Sampler subclass of `PubResult`), and every V2 job — the local `PrimitiveJob` as much as `RuntimeJobV2` — is an instance of `BasePrimitiveJob`, whose interface is `result`, `status`, `done`, `running`, `cancelled`, `in_final_state` and `cancel`. — ⚙️ proven in [`s7-q036`](/docs/sections/s7)

## Monitor jobs

### The job handle: string states, predicates, and the one blocking call

`sampler.run(...)` and `estimator.run(...)` return a `RuntimeJobV2` immediately — the job itself executes server-side. Everything you do with it afterwards splits cleanly into cheap non-blocking queries and one blocking call.

`job.status()` is the cheap query. In `qiskit-ibm-runtime` 0.4x it returns a PLAIN STRING, typed in the API reference as `Literal['INITIALIZING', 'QUEUED', 'RUNNING', 'CANCELLED', 'DONE', 'ERROR']`, which is exactly why the official examples write `if j.status() == "DONE"`. It is NOT a `JobStatus` enum member — the V1 enum is still importable and compares False against every one of these strings, so a polling loop written against it never exits. It also does not block, does not return a `(state, queue_position)` tuple, and carries no queue information; queue position is a Workloads-page / `job.metrics()` concern.

`job.result()` is the blocking call: it waits until the job reaches a terminal state and then returns the `PrimitiveResult`. It never returns partial shots, so 'poll `done()` because `result()` returns early' is backwards. Around those two sit the boolean predicates built on the same string: `done()` (literally `status() == "DONE"`), `errored()`, `cancelled()`, `running()` and `in_final_state()`, plus `wait_for_final_state(timeout, poll_interval)` for a blocking poll without fetching data. The class constant `JOB_FINAL_STATES` is `('DONE', 'CANCELLED', 'ERROR')` — three terminal states, and note that CANCELLED is one of them. Other useful members: `job_id()`, `backend()`, `error_message()`, `logs()`, `metrics()`, `usage()` and `usage_estimation`.

Cancelling is a job-handle operation: `job.cancel()` asks the service to drop the job, after which `status()` reports the terminal `"CANCELLED"` — a state change, not a deletion, and `in_final_state()` becomes true. There is no `job.stop()` and no `QiskitRuntimeService.cancel()`; the service is for FINDING jobs (`job`, `jobs`) while the job object owns the lifecycle. A cancelled job yields no partial data — calling `result()` on it raises rather than handing back the shots collected so far. And because the job runs server-side, deleting your local variable or restarting the kernel leaves it queued and still consuming your instance's time. The same cancel action is available from the Workloads page in IBM Quantum Platform.

One removal to recognise: `qiskit.tools.job_monitor` disappeared with Qiskit 1.0 and does not exist in 2.x. Monitoring in modern code is `status()` in a loop, `wait_for_final_state()`, or the Workloads page.

### Watching a session, and the platform-side view

Beyond individual jobs, the exam expects you to know what a `Session` can tell you about itself. `session.details()` returns a DICTIONARY describing the SESSION, not its jobs. The documented keys include `id`, `backend_name`, `state` (one of open, active, inactive, closed), `accepting_jobs`, `max_time` (the maximum allowed session length in seconds, subject to plan limits), the lifecycle timestamps `started_at`, `activated_at`, `last_job_started`, `last_job_completed` and `closed_at`, plus `interactive_timeout`, `active_timeout`, `mode` and `usage_time`. What is NOT in there: anything per-job. A `queue_position` belongs to a job, and `results` belong to `job.result()` — a session never carries result data. One practical gotcha: in local testing mode (a `Session` built on a fake backend) there is no server-side session to describe, so `details()` returns `None`, and `session_id` is `None` too.

The rest of the session surface is small and shared with `Batch`: `backend()`, `status()`, `usage()`, `close()`, `cancel()`, `from_id(session_id, service)` and the `service`/`session_id` attributes. The two lifecycle verbs are easy to confuse and are examined on the difference: `close()` stops the session ACCEPTING new jobs while existing queued and running jobs run to completion, and the session terminates once nothing is pending; `cancel()` cancels all PENDING jobs in the session. Neither class exposes a public `run` — you always run through a primitive constructed with `mode=session`.

The browser side matters too, because several official answers point at it. The Workloads page on IBM Quantum Platform lists every workload you submitted with its Status column and its job ID — that is the documented route when you never recorded an ID programmatically — and it is where you cancel a job without Python (overflow menu → Cancel on the row, or the Actions dropdown on a workload's detail page). The Instances table shows total time used and remaining on your plan, and the Analytics page counts jobs plus batch and session workloads, for accounts you own or manage.

Finally, keep the retrieval-vs-monitoring boundary crisp, since one question shape mixes them deliberately: `service.jobs(...)` FINDS jobs (filters, `limit` defaulting to 10, and it also returns jobs from the deprecated `qiskit-ibm-provider` package), `service.job(id)` fetches one, and everything about state — status, cancellation, waiting — is a method on the job object you get back.

- `RuntimeJobV2.status()` is typed `Literal['INITIALIZING', 'QUEUED', 'RUNNING', 'CANCELLED', 'DONE', 'ERROR']` — a plain STRING, not a `JobStatus` enum member, which is why official examples write `j.status() == "DONE"`. — 📖 [runtime-job-v2](https://quantum.cloud.ibm.com/docs/api/qiskit-ibm-runtime/runtime-job-v2)
- `JOB_FINAL_STATES` is `('DONE', 'CANCELLED', 'ERROR')`, and `done()`, `errored()`, `cancelled()`, `running()` and `in_final_state()` are the boolean predicates built on the state; `wait_for_final_state(timeout, poll_interval)` polls until a terminal state. — 📖 [runtime-job-v2](https://quantum.cloud.ibm.com/docs/api/qiskit-ibm-runtime/runtime-job-v2)
- `job.result()` is the BLOCKING call — results are available only after the job completes — while `job.status()` is the cheap state check and `job.job_id()` returns the ID you need to retrieve the job later. — 📖 [monitor-job](https://quantum.cloud.ibm.com/docs/guides/monitor-job)
- Cancellation is a job-handle operation: `job.cancel()` in Qiskit, or the Cancel action on the Workloads page; `cancel()` raises `RuntimeInvalidStateError` if the job is in a state that cannot be cancelled. — 📖 [runtime-job-v2](https://quantum.cloud.ibm.com/docs/api/qiskit-ibm-runtime/runtime-job-v2)
- `service.jobs()` is the listing call: `limit` defaults to 10 and it filters on `backend_name`, `pending`, `session_id`, `created_after`/`created_before` (datetime objects) and more; use it when you did not record a job ID. — 📖 [monitor-job](https://quantum.cloud.ibm.com/docs/guides/monitor-job)
- `session.details()` describes the SESSION: `state` (open/active/inactive/closed), `accepting_jobs`, `max_time`, `started_at`/`activated_at`/`last_job_started`/`last_job_completed`/`closed_at`, and `usage_time`. - `session.close()` stops the session accepting NEW jobs while queued and running jobs finish; `session.cancel()` cancels all pending jobs in the session — two different verbs. — 📖 [session](https://quantum.cloud.ibm.com/docs/api/qiskit-ibm-runtime/session)
- The Workloads page lists every submitted workload with its Status column and job ID (the documented route when no ID was saved); the Instances table shows plan time used/remaining and the Analytics page counts jobs, batches and sessions. — 📖 [monitor-job](https://quantum.cloud.ibm.com/docs/guides/monitor-job)

- `details()["state"]` and `session.status()` use different vocabularies: `open`/`active`/`inactive`/`closed` for the field versus `Pending`, `In progress, accepting new jobs`, `In progress, not accepting new jobs`, `Closed` for the call. `interactive_timeout` is the idle gap allowed between jobs, `active_timeout` how long it may stay active, `max_time` the total session length, `usage_time` the QPU-committed time. — 📖 [session](https://quantum.cloud.ibm.com/docs/api/qiskit-ibm-runtime/session)
